### MP推定式の扱い

wiki には Lv.1 と Lv.110 の2点しかないため `MP(Lv) = MP(Lv.1) × (1 + 0.01 × (Lv-1))` で外挿。
既知データで検算したところ、スター以外71件中69件が一致。例外はオデッセイ/スプリングトラップ（×2.10）と
スター4件（×1.99 = Lv.100相当）。

**ユーザーからも「合っているかは分からないが一旦それで」との回答**だったため、
UIに推定値である旨を明示し、`docs/skill.md` に「⚠ 推定・未検証」として検算結果・例外・更新方法を記載。
式は `getMpAtLevel()` の1箇所に閉じ込めてあるので、実測が出たら差し替えるだけで済む。

### 追加の学び
- **UI設計の指摘は自分では気づけない類が多い。** 代表画像の整合、デフォルト並び順、
  数値のレンジ、ナビの切り方。→ `tsukiusa-loop` に「UI設計で外しやすい点」として追記
- wiki の画像は**大文字拡張子 `.PNG` だと簡易ヘッダーの curl が403**になる。
  失敗するとHTMLが .png として保存されるので `file` での検証が必須 → `tsukiusa-research` に追記
- zsh の `path` は `PATH` に連動する特殊変数。`while read -r id path` でPATHが壊れた → 同上

### Phase 4: フィードバック2巡目

| 指摘 | 対応 |
|---|---|
| IAは「武器」「スキル」の分類でよかった | 前周で「図鑑/ツール」に変えたが、実物を見た上で**武器/スキルに戻した**。ホームのカード順も戻す |

| 各等級の中は属性（光→闇→火→水）でまとめてほしい | 属性順を第1ソートキーにし、選択した並べ替えは属性のまとまりの中に効かせる |

### 学び（2巡目）
- **IAは机上で決めきれない。** 「図鑑/ツール」案は論理的には筋が通っていたが、実物を見たユーザーの判断は
  「武器/スキル」だった。案を出すより**動くものを見せて選んでもらう**方が速い
- **見出しごとに `<table>` を分けると列が揃わない。** グループ化された表は1つの table にまとめ、
  グループ見出しは `colSpan` の行で表現する。`colgroup` + `table-fixed` で幅を固定する
- `table-fixed` にすると溢れたセルが `truncate` で欠ける。**図鑑系で名前が省略されるのは致命的**なので
  列幅配分は実データの最長値で確認する

### 発見した既存データの誤り
| 誤り | 正 |
|---|---|
| スキルの上限は全等級 Lv.110 | **スタースキルのみ Lv.100**。一覧ページ(140)のヘッダーが全等級「MAX (lv.110)」で統一されていたのが原因 |
| スキルルーンの確率は全スキル共通 | **スタースキルだけ別**（マジック39% + スター1%が入る） |

副次的な収穫として、スターの上限が Lv.100 と判明したことで **MP推定式の裏付けが取れた**。
前周「スターだけ倍率1.99でずれる」と書いたのは上限の誤認が原因で、Lv.100 なら `1 + 0.01 × 99` = 1.99 と完全一致する。

### 学び
- **データ取得の詰まりどころ**: 30KBのJSONをブラウザから持ち出そうとして、
  ローカルHTTPへのPOST（CSPで不可）→ クリップボード（ユーザー操作が必要で不可）と2回失敗した。
  正解は **curl にブラウザ相当のヘッダーを付けてサーバー側で取得**すること。
  wikiページは画像と同じくヘッダーさえ揃えば curl で取れる。最初からこれを試すべきだった
- **企画は選択肢を出して選んでもらう。** 実装の詳細を先に詰めようとして質問を返された。
  「何を作るか」の案を並べるのが先で、「どう作るか」は決まってから
- **既存データの誤りは新しい範囲を調べたときに出てくる。** 一覧ページだけ見ていたときは
  気づけなかった上限レベルの誤りが、個別ページを見た瞬間に判明した
