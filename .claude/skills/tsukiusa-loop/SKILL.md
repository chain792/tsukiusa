# 攻略サイト改善ループ

`リサーチ → 企画 → 実装 → フィードバック` を1周する。**1周で1〜2機能**に絞ること。大きく広げない。

## 状態の置き場所

| ファイル | 役割 |
|---|---|
| `docs/ideas.md` | アイデアのバックログ。ステータス（未着手/実装中/完了/却下）付き |
| `docs/loop-log.md` | 各周回の記録（日付・やったこと・学び） |
| `docs/patchnotes/` | パッチノート要約 |
| `docs/weapon.md` / `synthesis.md` / `gacha.md` | ゲームデータの正 |

ループの最初に `docs/loop-log.md` と `docs/ideas.md` を読み、前周の続きから始める。

---

## Phase 1: リサーチ

`tsukiusa-research` スキルを使う。

やること:
- 前回のループ以降に出たパッチノートを読み、`docs/patchnotes/` に追加
- @wiki で数値の変更がないか確認（特に `武器`(305)）
- 見つかった「サイトに載っていない情報」を `docs/ideas.md` に候補として追記

**差分がなければ Phase 1 はスキップしてよい。** 毎回フルスキャンする必要はない。

## Phase 2: 企画

`docs/ideas.md` から次にやる 1〜2 個を選ぶ。選定基準:

1. **ユーザーが実際に困っていること**を解決するか（計算が面倒 / 情報が散在している）
2. **既存データで作れるか**（新規データ収集が要るものは Phase 1 に戻す）
3. **既存ページと重複しないか**
4. **公式wikiに対して優位性があるか** — 単なるデータの再掲は価値が薄い。
   絞り込み・並べ替え・**wikiに無い計算指標**のいずれかを必ず載せる
   （例: スキル図鑑の「MP/秒」= MP消費 ÷ クールタイム）
5. **運用コストが釣り合うか** — 期間限定情報（クーポン、開催中イベント）は
   追随できないと「古い情報が並ぶページ」になって逆効果。実装が簡単でも却下しうる

企画したら `AskUserQuestion` で方向性を確認してから実装に入る。ここを飛ばすと手戻りが出る。
**実装の容易さと価値は別物。** データが揃っているからという理由だけで選ばないこと。

## Phase 3: 実装

規約は `CLAUDE.md` と `docs/app.md` に従う。特に:

- UIコンポーネントは `src/components/ui/`、機能別は `src/components/{機能名}/`
- **テキストは必ず `src/i18n/ja.ts` と `en.ts` の両方に追加**。ハードコード禁止
- 新ページは `src/pages/` と `src/pages/en/` の両方を作る
- 武器名は `getWeaponDisplayName(name, locale)`、スキル名は `getSkillDisplayName(skill, locale)` を使う
- ゲームデータは `src/lib/{領域}/` に `data.ts` / `constants.ts` / `utils.ts` / `index.ts` の構成で置く
  （`src/lib/weapons/`, `src/lib/skills/` が前例）
- 新ページを足したら **サイドバー（`src/layouts/Layout.astro`）とホームのカード（`src/components/home/HomePage.tsx`）にも追加**する。忘れやすい

完了条件:
- [ ] `npx tsc --noEmit` が通る
- [ ] `npm run build` が通る
- [ ] `npm run dev` で日本語・英語の両方を実機確認（Chrome拡張でスクリーンショット）
- [ ] 日英ページの両方を実機確認した（片方だけだと翻訳漏れに気づけない）
- [ ] モバイル幅で横スクロールが出ないことを確認した（`tsukiusa-research` の検証スニペット）
- [ ] 関連する `docs/` を更新した
- [ ] **docs に書いた数値をコードから検証した**（等級別件数、倍率などは手で書くと間違える）

## Phase 4: フィードバック

1. 実装したものをスクリーンショット付きでユーザーに見せる
2. フィードバックをもらう
3. **その場で直せるものは直す**
4. 次のループに持ち越すものは `docs/ideas.md` に戻す

### ループを閉じる（重要）

毎周、必ず以下を更新してから終わる:

- `docs/loop-log.md` に1エントリ追記（日付 / やったこと / もらったFB / 次にやること）
- `docs/ideas.md` のステータス更新
- **このスキルと `tsukiusa-research` スキル自体を見直す** — 詰まった箇所・手順が違った箇所があれば書き換える。手順書は使いながら育てる
- ゲーム仕様の新しい理解は `docs/` の該当ファイルへ

## UI設計で外しやすい点（実際に指摘されたもの）

- **代表画像はそのページの中身に合わせる。** スキルのページに武器画像を置くと違和感が出る。
  素材が無ければ wiki の個別ページ添付画像を取れる（`tsukiusa-research` 参照）
- **一覧のデフォルト並び順は「名前順」にしない。** ゲーム内で意味のあるまとまり（等級など）で
  まずグループ化し、並べ替えはグループ内に効かせる
- **数値はプレイヤーの実際の到達レンジに合わせる。** wiki の表記（例: スキルLv.110）が
  現行の上限とは限らない。実プレイの感覚とズレていないかを確認する
- **ナビゲーションの切り方は机上で決めきらない。** 「図鑑/ツール」のような性質での分割と
  「武器/スキル」のような対象での分割はどちらも筋が通る。案を並べて聞くより、
  **一方を実装して見せて選んでもらう**方が速い（このプロジェクトでは対象別＝武器/スキルに決着）
- **グループ化した表は1つの `<table>` にまとめる。** グループごとに table を分けると
  それぞれ独立して列幅を計算するため**列位置がずれる**。`colgroup` + `table-fixed` で幅を固定し、
  グループ見出しは `colSpan` を張った行で表現する
- **`table-fixed` + `truncate` で名前が欠けていないか確認する。** 図鑑系で項目名が省略されるのは致命的。
  列幅配分は実データの最長値で検証すること

## 出典が2点しかない値の扱い

wiki が Lv.1 と Lv.110 のような**飛び飛びの2点**しか載せていないことがある。
そこから外挿するときは:

1. 式を立てたら **既知の全データで検算**し、一致率と例外を数える
2. `AskUserQuestion` で式を提示して確認する（ユーザーも即答できないことがある）
3. 確定しないまま進める場合は、**UIに推定値である旨を表示**し、
   `docs/` に「⚠ 推定・未検証」と検算結果・例外・更新方法を書く
4. コードは `getXxxAtLevel()` のように**式を1箇所に閉じ込める**（実測が出たら1関数の差し替えで済む）

## 進め方の原則

- **1周を小さく。** 完璧な1ページより、動く小さな改善を積む
- **推測でゲーム数値を埋めない。** 不明ならユーザーに聞く（`tsukiusa-research` の §5）
- 実装前に必ず既存コードを読む。同じ計算ロジックが `src/lib/weapons/` にすでにあることが多い
